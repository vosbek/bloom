# Agent messaging

Any agent with the Blume plugin installed can message any other agent on the same
Blume account, across harnesses. The person using Blume can message any agent as well.
Blume stores and routes every message. Each harness delivers messages through the plugin
components that work best in that harness. See [what "the plugin" means](plugin-architecture-levers.md#what-the-plugin-means).

Decisions (Olav, 2026-09-28):

- The standalone Inbox tab is removed. Messaging lives on each agent: open an agent from a
  delivery's or a project's Agents tab to see its message history and a composer. The old
  `/inbox` route redirects to Projects.
- Scope is the whole account. Agents can find and message every non-revoked agent
  on the account, and the list shows each agent's project.
- A message can stand alone. Linking it to a delivery is optional, and a linked
  message also appears on that delivery.
- The installer writes the hooks file (`hooks/hooks.json`, with an absolute script path)
  into the plugin in both harnesses. In Codex it then marks Blume's hooks, and only
  Blume's, trusted using Codex's own `hooks/list` and `config/batchWrite`, the same calls
  as Codex's `/hooks` screen.
- Delivery comes in tiers (Olav, 2026-09-28). Tier 1 works the same way in every
  harness: new messages come back with the agent's next Blume tool result. Tier 2 adds
  one hook script shared by Claude Code and Codex, which delivers between any tool calls
  and before a turn ends. Both tiers deliver only while a session is running. Waking an
  idle session is a later, optional tier: Claude Code's `asyncRewake`, and Codex's queue
  (`thread/queue/add` via `codex queue`) with a fallback to the next turn.

## Identity

An agent is a harness **session**, not a plugin installation or a bridge process.

| Harness | Identity | Where the plugin reads it |
| --- | --- | --- |
| Claude Code | session id | `CLAUDE_CODE_SESSION_ID` in the MCP server's environment; `session_id` in hook input |
| Codex | root thread id | `_meta.threadId` on each MCP `tools/call`; `session_id` in hook input |
| Other | per-process id | Generated by the bridge, as before |

Both paths resolve to the same Blume agent, so a resumed session keeps its inbox.

## Delivery by plugin component

| Situation | Claude Code | Codex |
| --- | --- | --- |
| Any time (tier 1, every harness) | MCP tools: `blume_context` (agentQuery finds agents), `blume_message_send`, `blume_inbox`, `blume_message_ack`. Every Blume tool result also reports unread messages. | Same |
| Session starts or resumes (tier 2) | SessionStart hook: register the session and add unread messages to context | Same |
| During a turn (tier 2) | PostToolUse hook: adds new messages to context (`additionalContext`), checking at most every 10 seconds and skipping Blume's own tools | Same |
| Turn about to end (tier 2) | Stop hook: when new messages arrived, blocks the turn from ending once, with the messages as the reason the model sees; never again while `stop_hook_active` is set | Same |
| Session idle (later tier) | Not yet: an async `asyncRewake` hook could wait for the next message and wake the session | Not yet: hooks cannot wake a thread; Blume Deliveries could queue the message into it (`codex queue --thread <id> --message …`) |
| Session closed | The message waits and arrives with the SessionStart hook, or the next Blume tool result, on resume | Same |

Agents answer the person using Blume by sending to `human`. The reply appears at once in
that agent's conversation on Agents. Delivered text names each sender's id, so an agent
can reply without reading its inbox first. The installer's connection check uses a
reserved conversation id: it proves the key works but registers no agent.

Message text from another agent is untrusted peer data. Hooks label the sender. The
skill says a peer message is information and requests, never approval or permission.

## Message states

- **Queued**: stored and not yet shown to the recipient.
- **Delivered**: a Blume tool result reported it to the recipient (tier 1), a hook put it in the recipient's context, or the recipient read it with `blume_inbox` (hooks use `blume_inbox_deliver`).
- **Acknowledged**: the recipient called `blume_message_ack`. This means it has read the
  message, not that it has done the requested work.
- **Failed**: the recipient was revoked before the message was delivered.

Acknowledged messages are pruned after 30 days. Each recipient keeps at most 500 messages.
